> 项目名称: YepAnywhere
> 版本基准: 0.4.28

## 1. 项目背景与问题陈述

### 1.1 行业背景

2025-2026 年，AI 编码代理（Coding Agents）成为开发者工具的重要分支。Claude Code、Codex CLI、Gemini CLI 等工具可以在终端中自主完成代码编辑、测试、Git 操作等任务。然而，这些工具都是**终端原生**的：

- 需要长驻终端会话
- 等待用户批准时阻塞执行
- 无法从手机等移动设备交互
- 多会话管理依赖多个终端 tab

### 1.2 核心痛点

| 痛点编号 | 问题描述 | 影响程度 |
|----------|----------|----------|
| P1 | **移动端无体验**：终端等宽字体在小屏幕上极难阅读 | 高 |
| P2 | **无法及时响应**：AI 等待批准时用户离开电脑，任务阻塞 | 高 |
| P3 | **多会话分散**：多个项目/多个代理在不同终端中，状态不聚合 | 高 |
| P4 | **无文件上传**：手机相册中的截图/设计稿无法直接发给 AI | 中 |
| P5 | **无推送通知**：必须主动查看终端才知道 AI 是否需要帮助 | 中 |

### 1.3 解决方案定位

YepAnywhere 定位为"AI 编码代理的移动监督台"：不改变 AI 代理的运行方式（仍在本地 CLI 运行），而是在其上叠加一个移动友好的远程控制层。

## 2. 需求规格说明书

### 2.1 功能需求

#### FR-1 会话管理
- **FR-1.1** 自动扫描并列出所有 Claude / Codex / Gemini 项目
- **FR-1.2** 查看任意会话的完整消息历史
- **FR-1.3** 在会话中发送新消息（文本 + 文件附件）
- **FR-1.4** 创建新会话（选择项目、模型、权限模式）
- **FR-1.5** Fork/Clone 会话（从任意消息节点分支）
- **FR-1.6** 归档/星标/重命名会话

#### FR-2 实时交互
- **FR-2.1** 流式接收 AI 响应（SSE/WebSocket）
- **FR-2.2** 批准/拒绝 AI 的工具调用请求
- **FR-2.3** 切换权限模式（Approve Once / Approve All / Auto-reject）
- **FR-2.4** 语音输入（浏览器 Speech API）

#### FR-3 文件与媒体
- **FR-3.1** 从手机相册上传图片/PDF/代码文件
- **FR-3.2** 查看 AI 生成的代码差异（Diff 视图）
- **FR-3.3** 浏览项目文件树
- **FR-3.4** 查看 Git 状态（变更文件列表）

#### FR-4 远程访问
- **FR-4.1** 从互联网任何位置连接家中服务器
- **FR-4.2** 端到端加密（Relay 不可见内容）
- **FR-4.3** 无账户体系（SRP-6a 用户名密码即可）
- **FR-4.4** 支持自托管 Relay

#### FR-5 通知与聚合
- **FR-5.1** Web Push 推送（需要批准时通知锁屏）
- **FR-5.2** 分层收件箱（Needs Attention / Active / Recent / Unread）
- **FR-5.3** 全局活动流（所有代理的实时状态）
- **FR-5.4** 未读消息计数和标记

#### FR-6 设备控制
- **FR-6.1** Android 模拟器屏幕流式传输（WebRTC）
- **FR-6.2** 触摸输入映射（多点触摸、滑动）
- **FR-6.3** 自适应视频质量（根据网络调整码率）

#### FR-7 设置与管理
- **FR-7.1** 运行时修改端口和网络绑定
- **FR-7.2** Cookie 认证开关和密码修改
- **FR-7.3** 远程访问配置（Relay 地址、用户名）
- **FR-7.4** 提供商启用/禁用（Claude/Codex/Gemini 等）
- **FR-7.5** Ollama 本地模型配置

### 2.2 非功能需求

| 编号 | 需求 | 目标值 |
|------|------|--------|
| NFR-1 | 首屏加载时间 | < 2s（3G 网络）|
| NFR-2 | 消息端到端延迟 | < 500ms（本地）/ < 2s（远程）|
| NFR-3 | 并发会话支持 | >= 20 个活跃进程 |
| NFR-4 | 移动端适配 | iOS Safari + Android Chrome 全功能支持 |
| NFR-5 | 离线能力 | PWA 缓存核心静态资源 |
| NFR-6 | 数据安全 | E2E 加密 + 无密码存储 |
| NFR-7 | 安装复杂度 | 单命令启动（`npx yepanywhere`）|
| NFR-8 | 内存占用 | 空闲时 < 200MB |
| NFR-9 | 日志保留 | 默认 7 天轮转 |
| NFR-10 | 向后兼容 | 新版本能读取旧版本的 session-metadata.json |

### 2.3 用户画像

####  persona-1: 移动开发者 Alex
- 28岁，全栈开发者，使用 Claude Code 辅助编程
- 常在咖啡馆/通勤途中用手机查看 AI 进度
- 痛点：离开电脑后不知道 AI 是否卡住或已完成
- 使用场景：锁屏收到推送 → 快速批准工具调用 → AI 继续运行

#### persona-2: 远程团队 Lead Sarah
- 35岁，技术负责人，管理 3-5 个项目的 AI 代理

- 痛点：多个终端 tab 难以管理，错过关键批准请求

|----------|----------|------|------|

| 上传文件 | `~/.yep-anywhere/uploads/` | Binary | 写 |

## 4. 技术选型与依据

### 4.1 Hono 而非 Express

| 考量 | Hono | Express |
|------|------|---------|
| 包体积 | ~16KB | ~208KB |
| 启动时间 | <50ms | ~200ms |
| TypeScript | 原生（无需 @types）| 需额外类型包 |
| WebSocket | @hono/node-ws 官方维护 | 社区方案碎片化 |
| 运行时 | Edge + Node | 仅限 Node |
| 结论 | **选择 Hono** | — |

### 4.2 无数据库架构

**论证**：
- 数据源单一：Claude CLI 已经用文件系统做了持久化
- 引入数据库会造成双写问题（CLI 写文件，我们写 DB）
- 目标用户是开发者，"零配置"比"查询性能"更重要
- 会话量预期：个人用户 <1000 个会话，文件系统足够

**缓解措施**：
- SessionIndexService 做内存缓存
- proper-lockfile 做并发控制
- 定期全量验证保证索引一致性

### 4.3 SRP-6a + TweetNaCl 而非纯 TLS

**论证**：
- TLS 在 Relay 处终止，Relay 运营商可见明文
- SRP 实现**无密码存储**（服务器只存 verifier）
- E2E 加密保证即使 Relay 被攻破也安全
- 无证书管理负担（自签名 HTTPS 是可选的）

### 4.4 VAPID Web Push 而非 Firebase/OneSignal

**论证**：
- 自托管原则：不依赖第三方推送服务商账户
- Web Push 标准是浏览器原生支持
- 无 SDK 集成成本
- 代价：需自行管理 VAPID 密钥对

### 4.5 Tauri 而非 Electron

**论证**：
- 安装包体积：Tauri ~5MB vs Electron ~150MB
- 内存占用：Tauri ~50MB vs Electron ~200MB
- 安全：Tauri 使用系统 WebView，攻击面更小
- 代价：WebView 兼容性差异（Edge/WebKit）

### 4.6 React 19 而非 Vue/Svelte

**论证**：
- 团队熟悉度（从代码风格推断）
- React 19 的并发特性有利于流式消息渲染
- 生态丰富（Shiki 的 React 组件、xterm.js 等）

## 6. 风险评估与缓解策略

### 6.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| Claude SDK  Breaking Change | 中 | 高 | 锁定 SDK 版本，CI 集成测试 |
| fs.watch 不可靠导致数据不同步 | 中 | 中 | 定期全量重扫 + 手动刷新按钮 |
| 无数据库导致并发数据损坏 | 低 | 高 | proper-lockfile + 备份机制 |
| Relay 服务不可用 | 低 | 中 | 支持自托管 Relay + 局域网直连 |
| 进程数达到 OS 上限 | 中 | 中 | 最大并发限制 + 队列机制 |

### 6.2 商业风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| Anthropic 官方推出竞品 | 高 | 高 | 差异化（多提供商、自托管、开源）|
| 用户不愿意自托管 | 中 | 中 | 提供一键 Docker / 托管服务 |
| 开源导致无法变现 | 低 | 中 | MIT 允许商业使用，靠服务变现 |

### 6.3 法律合规风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| Anthropic TOS 限制第三方界面 | 低 | 高 | 使用官方 SDK，不伪造认证 |
| 加密出口管制 | 低 | 低 | TweetNaCl/SRP 是公开算法 |

## 7. 商业模型分析

### 7.1 开源策略

- **许可证**: MIT（最宽松）
- **目的**: 快速获取开发者社区信任，降低试用门槛
- **代价**: 任何人可 forks 并竞争

### 7.2 变现路径

#### 路径 A: 托管 Relay 服务（已部分实现）
- **免费版**: 公共 Relay，带宽/连接数限制
- **付费版**: 自定义 Relay 域名、优先带宽、99.9% SLA
- **定价参考**: $5-10/月/用户

#### 路径 B: 企业版
- **功能**: SSO（SAML/OIDC）、审计日志、团队管理、LDAP
- **定价**: $20-50/月/用户
- **目标**: 10-100 人技术团队

#### 路径 C: 应用商店
- **iOS/Android 原生应用**（非 Tauri wrapper）
- **付费下载**: $4.99 或订阅制
- **增值功能**: 离线缓存、生物识别认证

#### 路径 D: 集成服务
- **云 IDE 集成**: GitHub Codespaces、Gitpod 预装
- **AI 提供商佣金**: 引导新用户注册 Claude/Codex（ affiliate ）

### 7.3 目标市场

| 市场细分 | 规模估算 | 优先级 |
|----------|----------|--------|
| 个人开发者（免费用户）| 100K+ | P1（获客）|
